# 共通ルール

出力言語にかかわらず適用する、文書の目的・構成・内容の分かりやすさの規則です。
文体・語彙・表記と、文の長さの基準は、出力言語のファイル（`locales/<言語>.md`）に書いています。

各節の冒頭に狙いを書いています。列挙にない場面に出会ったら、狙いに照らして判断してください。
規則の文面より狙いを優先します。

## 前提

狙いは、読み手が読み返さずに行動できる状態にすることです。
そのため、高校生が文章を読み、そのまま作業できる平易さを基準にします。
書き手が分かっている内容は、読み手には共有されていません。

- 前提知識なしで、文章の意味が分かる書き方をすること。
- 一度読んで分からない文は、書き直すこと。読み返しが必要な時点で、書き手の責任である。
- 読み手が省略した情報を補完してくれると想定しないこと。
- 比喩は原則使わず、具体的な説明をすること。
  - トピックの領域外の専門用語を比喩に使わないこと。説明のつもりが、比喩の意味を考える手間を増やす。
  - 特に数学、宗教、形状、法律を比喩に使用することは一般的ではないので明確に禁止。
- 「具体的」とは、読み手がユースケース（だれが、どんな場面で、何をしようとして使うか）を想像できることを指す。実測値を並べることではない。

  避ける: 起動時間が 1.2 秒から 0.4 秒になりました（数値だけで、だれがどう助かるかが分からない）
  書く:   アプリを開くたびに待たされていた人が、開いてすぐ作業に入れます

## 構成

狙いは、読み手が冒頭だけで判断できるようにすることです。
読み手は最後まで読んでから判断するとは限りません。結論が末尾にあると、
途中で読むのをやめた人には何も伝わりません。

- 1文目から本題に入り、結論の文で終えること。
- 経緯・前提・断り書きを先に置かないこと。必要なら結論のあとに書く。
- 散文を基本とすること。箇条書きは列挙のために使う。
  流れのある説明を箇条にすると、項目間の関係が消える。
- 同類の項目が3つ以上並ぶときは箇条書きにすること。2つ以下は散文で書く。
- 各項目に2つ以上の観点があるときは表にすること。
- 見出しと太字は、節が3つ以上あるときだけ使うこと。
  短い文章に見出しを付けても、探す手間が減らない。
- 太字は用語・ファイル名・値に限ること。文の一部を強調するために使わない。
  強調が増えるほど、どれも目立たなくなる。
- 末尾に要約や「以上です」を付けないこと。結論で終えるのと要約を足すのは別である。

## 文と段落

狙いは、1文を1回で読み取れる情報量に保つことです。
文字数や句読点の数のように、言語で変わる基準は、出力言語のファイルに従います。

- 一文一意とすること。
- 述語が2つ以上ある文は分けること。
- 1段落は3文程度とすること。
- 既定は短くすること。ただし説明・理由・詳細を求められたときは、長さを気にせず必要なだけ書く。
  短さは目的ではなく、読み手が求めた情報を削る理由にはならない。
- 疑問を投げかけないこと。成果物は返事を受け取れないので、断定して書く。

## 肯定形と否定形

狙いは、読み手が次に何をすればよいかを、文から直接読み取れるようにすることです。

- 二重否定を使わないこと。肯定形に直す。読み手が否定を2回たどることになり、
  意味を取るのに時間がかかる。

  避ける: 動かないわけではありません
  書く:   動きますが、条件があります

  避ける: 設定が不要なケースがないとは言えません
  書く:   設定が要らない場合もあります

- 1文に否定を2つ以上入れないこと。条件節と主節の両方が否定になったら、文を割る。
- 禁止を伝える場合を除き、肯定形で書くこと。何をしてはいけないかを読んでも、
  読み手は次に何をすればよいか分からない。

  避ける: このオプションを付けないと動きません
  書く:   このオプションが必要です

  避ける: 型が一致しない場合はエラーになります
  書く:   型が一致したときだけ通ります

- 禁止・制約・危険の警告は否定形のままでよい。肯定形に直すと危険度が伝わらなくなる。
  「削除は取り消せません」を「削除する前に確認してください」に変えない。

## 語の選び方

狙いは、読み手が書き手と同じ判断に到達できる語を選ぶことです。

- 「効率的に」「柔軟な」「非常に重要」のような評価語は、使う場面・条件・根拠に置き換えること。
  評価語だけでは、読み手が同じ判断に到達できない。数値は、読み手の判断に要るときだけ添える。
- 接続詞は論理関係が変わる箇所にだけ置くこと。毎文に置くと、どこで話が転換したのか分からなくなる。

技術用語、エラーメッセージ、コマンド、ライブラリ名、API のフィールド名、設定キー、
仕様書の用語は原文のまま使い、訳しません。訳語を作ると検索できなくなります。
引用したエラーメッセージ、コード中のコメントと識別子は、このファイルと出力言語のファイルの、文体と語彙の規則の対象外です。

## 校正で確かめる項目

| 項目 | 直し方 |
| :-- | :-- |
| 表記ゆれ | 同じものは同じ語で書く。「アイデア」と「案」を混ぜない。技術文書では、同じ語の繰り返しを類語に言い換えない |
| 記号のゆれ | かっこ・引用符・中黒の使い方を文書内でそろえる |
| 相対的な日時 | 「昨日」「来週」を日付に直す |
| 指示語 | 「これ」「その件」が指すものが前の文から1つに決まらなければ、名詞に直す |
| 「など」の多用 | 具体例を3つ挙げるか、「など」を消して全部を列挙する |
| 文書の外への参照 | 「前回の件」「例の資料」は、日付・資料名・リンクを添えて、文書だけで分かる形にする |
| ローカルにしかない情報 | 読み手が見られない情報（手元の絶対パス、端末名、手元の環境の設定値、会話でのやりとり）は一般化する。パスはファイル名・資料名で呼ぶ。例: `C:\Users\<名前>\work\setup.md` →「セットアップ手順（setup.md）」 |
| 個人情報 | 氏名、メールアドレス、電話番号、アカウント名、社員番号、顧客のデータは、`<氏名>` や `user@example.com` のような置き換え用の値に直す。全文を載せるエラーメッセージやログでも、個人情報の部分だけは置き換え、置き換えたことを書く。ただし、文書の対象として本人が公開している情報（公開リポジトリの URL、作者名のクレジット）は置き換えない |
| 読み手が開けない場所への参照 | 「実測値は `~/dir` にあります」のように、手元にしかない場所を根拠の置き場にしない。判断に要る値は本文に書く。量が多ければ、リポジトリ・共有フォルダなど読み手が開ける場所に置いてリンクする。置けなければ、根拠を共有していないことを本文に書く |

## 全文を示すもの

次のものは省略も要約もせず、全文をそのまま載せてください。
要約した時点で、読み手が原因を特定する手段が失われます。

- エラーメッセージとスタックトレース
- セキュリティ上の警告
- 取り消せない操作の確認(削除、強制 push、マイグレーション、外部への送信など)
