# description が、スキルが呼ばれるかどうかを決める理由

`description` は、エージェントがスキルを呼ぶかどうかを判断するときに読む、ただ1つの説明文です。
この文書では、`description` がその役割を負う理由と、書き方について資料が述べていることを説明します。事実の出典は、末尾の「出典」に並べた資料です。

## description とは

`description` は、`SKILL.md` の frontmatter に書く必須の項目です。スキルがすることと、使う場面を書きます。上限は1024文字です。

## なぜ description を理解するのか

本文をどれだけ丁寧に書いても、スキルが呼ばれなければ、本文は読まれません。
`description` が使う場面を伝えていないと、エージェントはスキルを呼ばずに作業を進めます。範囲を広く書きすぎると、関係のない依頼でも呼ばれます。

## スキルが読み込まれる仕組み

エージェントは、スキルを3つの段階に分けて読み込みます。

| 段階 | 読むもの | 読む時点 |
| :-- | :-- | :-- |
| 1 | すべてのスキルの `name` と `description` | エージェントの起動時 |
| 2 | 呼んだスキルの `SKILL.md` の本文 | 依頼が `description` に合った時 |
| 3 | 本文が参照するファイル | 手順の中で要る時 |

依頼を受けた時点でエージェントが知っているのは、段階1の内容だけです。
そのため、呼ぶかどうかの判断材料は、`name` と `description` に限られます。本文に書いた「使う場面」は、判断のあとで読まれます。

## 別案と選ばなかった理由

別案は、すべてのスキルの本文を、起動時に読み込むことです。
資料は、この案を選ばなかった理由を直接には書いていません。書いているのは、次の2点です。

- 読み込んだ内容は、会話の履歴やほかの指示と、同じコンテキストの枠を分け合う
- 本文は呼ばれた時にだけ読むので、使われないスキルの本文は枠を使わない

ここから先は書き手の見方です。スキルが100個あるとき、全部の本文を先に読むと、依頼に使える枠が減ります。段階に分ける形は、その枠を残すための選択だと読めます。

## description の制約

`description` には、書く人が引き受ける制約があります。

- 1024文字の中で、すること、使う場面、使わない場面を伝える
- 説明が合っていても、呼ばれない依頼がある。エージェントが基本の道具だけで済ませられる1手順の依頼では、スキルを呼ばないことがある
- 呼ばれ方は実行のたびに変わる。資料は、同じ依頼を3回ずつ流して、呼ばれた割合で確かめる方法を挙げている

## 書き方について、資料が述べていること

書き方は、資料によって違います。

| 資料 | 文の形 | 書く内容 |
| :-- | :-- | :-- |
| Anthropic の資料 | 三人称で書く | することと、使う場面の両方 |
| agentskills.io の資料 | 「〜のときに使う」と、エージェントへの指示の形で書く | 利用者がしたいこと。スキルの内部の動きは書かない |

2つの資料は、文の形で食い違っています。どちらの形のほうがよく呼ばれるかを比べた計測は、どちらの資料にもありません。このリポジトリでも計測していません。
