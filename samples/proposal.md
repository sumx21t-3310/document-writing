# 提案: 公開前の手順に、発火テストを入れる

## 提案の要旨

`description` を変えたときは、公開の前に発火テストを流すことを、手順に入れる承認を求めます。
発火テストは、依頼の文を実際にエージェントに渡し、スキルが呼ばれた割合を数えるテストです。

## 課題

2026-10-05 に、`description` の語を書き換えました（コミット `a4ba30a`）。「次のときに使う:」を「発火:」に、「Do NOT use for:」を「対象外:」に変えています。
この変更のあとで、スキルの呼ばれ方が変わったかどうかは、計っていません。そのまま公開しました。

エージェントがスキルを呼ぶかどうかの判断材料は、`description` だけです（[explanation.md](explanation.md)）。
`description` を変えると、文書を頼んだ人の依頼でスキルが呼ばれなくなることがあります。コミットメッセージのような対象外の依頼で、呼ばれることもあります。いまの手順では、どちらも公開のあとで利用者が気づくまで分かりません。

## 目標と範囲

目標は、次の2つです。

- `description` を変える変更には、変更の前後の発火テストの結果が付いていること
- 変更後の結果で、用意した依頼のすべてが合格していること

合格の基準は、agentskills.io の資料が挙げている値を使います。

| 項目 | 値 |
| :-- | :-- |
| 依頼の数 | 約20件。呼ばれるべき依頼が8〜10件、呼ばれるべきでない依頼が8〜10件 |
| 1件あたりの実行回数 | 3回 |
| 合格の基準 | 呼ばれるべき依頼は、呼ばれた割合が 0.5 を上回る。呼ばれるべきでない依頼は、0.5 を下回る |

次のことは、範囲に入れません。

- スキルが書いた文書の質の評価
- Claude Code 以外のエージェントでのテスト

## 進め方

1. 依頼の文を約20件書き、`evals/trigger-queries.json` に置く。呼ばれるべきでない依頼には、コミットメッセージや3行以内の連絡のように、対象外と紛らわしい依頼を入れる
2. 依頼を1件ずつエージェントに渡し、スキルが呼ばれたかを記録するスクリプトを書く
3. いまの `description` で流し、結果を基準として保存する
4. README に、`description` を変えたときの手順として書く

## スケジュールと体制

作業は1人で進めます。承認の翌日に手順1と2を終え、その次の日に手順3と4を終えます。

## 費用

1回のテストで、エージェントを60回起動します（20件を3回ずつ）。変更の前後で流すと120回です。
1回の起動にかかる料金と時間は、計っていません。手順3で実際に流したときに記録し、この提案に追記します。

## リスクと対策

| リスク | 対策 |
| :-- | :-- |
| 用意した依頼にだけ合う `description` になり、ほかの依頼で呼ばれない | 依頼を、直すときに見る6割と、確かめるときだけ見る4割に分ける。資料が挙げている方法である |
| 結果が実行のたびに変わり、合否が安定しない | 1件を3回ずつ流し、割合で判定する。割合が 0.5 に近い依頼は、依頼の文を見直す |
| 依頼の文が実際の依頼と違い、テストが通っても利用者の依頼で呼ばれない | 過去に実際に頼まれた文を、依頼の文に使う |

## 別案との比較

| 案 | 選ばなかった理由 |
| :-- | :-- |
| いまのまま、公開してから様子を見る | 呼ばれなくなったことに、利用者が先に気づく。課題に書いた変更は、この進め方で公開した |
| 手で数件だけ試す | 結果が実行のたびに変わるので、1回ずつの試行では、変更の前後を比べられない |
| `skill-creator` スキルに任せる | 依頼の分割、テスト、`description` の改善案の作成までを自動で回せる。使うには、`skill-creator` を入れた Claude Code が要る。スクリプト1つで流せる形を先に作るために、今回は選ばなかった |
